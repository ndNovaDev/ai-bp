# ai-practice-pick

## 步 0 — 自然语言 → flag

| 用户说 | flag |
|---|---|
| 本周 / 这周 | `--this-week` |
| 上周 | `--last-week` |
| 最近 N 天 | `--recent Nd` |
| 上个月 / 上月 | `--last-month` |
| 本月 | `--this-month` |
| 2026-05 / 5 月 | `--month 2026-05` |
| 自 5 月 1 日以来 | `--since 2026-05-01` |
| 关于 X 的 / X 相关 | `--tag X` |
| 关于 X 或 Y 的 | `--tag X,Y` |
| 高分的 | `--min-score 80` |
| 前 N 条 | `--top N` |
| 不限 / 全部 | `--full` |
| 空 / 默认 | 无参数(全周期 score≥60 top 30) |

可叠加。下面用 `$FLAGS` 代指拼出来的串。

## 步 0.5 — 兜底 scan

```bash
node ${CLAUDE_PLUGIN_ROOT}/scripts/scan.js --recent 14d
```

报错或超时无碍。不向用户解释。

## 步 1 — 拉候选

```bash
node ${CLAUDE_PLUGIN_ROOT}/scripts/list.js $FLAGS
```

返回按 score 倒序的 JSON 数组。空数组 → 告诉用户"无候选,可放宽过滤或先 `/ai-practice-scan`",结束。

## 步 2 — 聚类 + 排名

下一条回复里贴 fenced JSON。同一件事的多个 session 合到一个 topic(信号:summary / tags / cwd / highlights 组合,同 cwd 不等于同 topic)。按"作为 OKR 周报案例的合适度"排 rank,保留前 8。

```json
{
  "topics": [
    {
      "title": "8-20 字事件名",
      "sessionIds": ["..."],
      "primarySessionId": "...",
      "rank": 1,
      "reason": "≤30 字:聚合理由 + 排序理由"
    }
  ]
}
```

## 步 3 — 用户挑 topic

`AskUserQuestion`(`multiSelect: true`),top 4:

- `label`: `[最高分 N|涵盖 M session] <title>`
- `description`: AI 的 `reason` + 日期跨度

用户勾 1-3 个。

## 步 4 — 取证(逐 topic)

按顺序取,够下笔就停。**core 是前两步,后两步是核对/补刀。**

1. **元数据**:`~/.ai-best-practice/data/index.jsonl` grep sessionIds,合 tags / filesEdited / 时间窗。框定 scope。
2. **user 消息原文**(主证据 — 用户的真实意图 / 卡点 / 转折):
   ```bash
   node ${CLAUDE_PLUGIN_ROOT}/scripts/lib/parse-jsonl.js --user-turns <jsonl-path>
   ```
   jsonl 路径在 index.jsonl 行的 `jsonlPath` 字段。输出按时间序的 `[ts]\n<text>\n---\n` 块,体量小(几十 KB 级)。这是周报唯一没被 Haiku 摘要过滤掉的"人话",assistant 输出不抽 — 那部分已经在 git 里物化。如需控量,加 `--max-chars 400`。
3. **git**(核对"做了什么" — 是否真落地):进 cwd,`git log --since=<起> --until=<止> --oneline`,关键 1-3 commit 跑 `git show --stat <hash>`,需要 patch 时只看怀疑的那个文件 `git show <hash> -- <file>`
4. **artifact**(补刀 patch 细节):filesEdited 挑 1-3 个,`Read` 加 offset/limit,一次 ≤ 200 行

**严禁**直接拿 index.jsonl 里 Haiku 生成的 `summary` / `highlights` 当起草素材 —— 那是二手压缩,起草锚到它就是在抄摘要,正是历代 reviewer 失败的根因(见 `scripts/lib/draft.js` 头注)。`summary` / `tags` 只用于步 2 聚类、步 3 选题。

## 步 5 — 采访(用户给方向,逐 topic)

写之前必须给用户开口的机会。Claude 不会读心 —— 光证据 + 四条方向能拼出"做了什么",拼不出**业务背景** / **用户想突出哪条线** / **哪些该砍**。哪怕用户只给一句"重点要 X、A 别写",都比模型凭空猜强一大截。

每个 topic 三小步,严格按顺序。

**5.0 — 背景盘点(承认自己不懂的地方)**

读完步 4 的证据后,Claude 在主对话里**先列一遍自己仍不清楚的背景**。证据能告诉你"代码上做了什么",告诉不了你:这件事的业务前因 / 谁是利益相关方 / 上下游怎么用 / 为什么这事值得周报。

清单条目示例(因 topic 而异,**别照抄**):
- 这个改动是谁提的需求 / 谁会用?
- 它和上下游哪些系统 / 团队有关联?
- 它解决的痛点是"踩过的事故"还是"主动优化"?
- 有没有 deadline 或外部承诺?

如果列下来有 2 条以上,**必须**走一次 `AskUserQuestion` 把缺口问清(`multiSelect: false` 或 free-form;一题塞多个问号可以,但别超过 3 问)。问到的回答和证据一并喂进 5.1。

如果 Claude 自查后觉得真没缺口(罕见),在主对话里写一句"背景已充分,跳过 5.0",再进 5.1。**不要默默跳过**。

**5.1 — Claude 草一段全文简述 + 显式列出"写什么 / 不写什么"**

草简述前,Claude 在内部按维度过一遍证据,列一份**素材盘点**(不展示给用户,直接消化进下面的方向 / 重点)。盘点只列已发生的事实,**素材空白的维度明确写"无 — 不补"**;绝不为了凑维度去写没做过的事。

6 维度(审稿 AI 真在看的,从 0508/0510 双批回测里抓的):

- **BID 业务集成深度**:用了哪些公司内部系统 / 数据 / MCP(CAT / Grafana / 飞书 Bitable / Drive / 内部表 / 服务……)。完全内部 = 满分,主要靠外部 = 低分。
- **TD 技术深度**:多步骤 agent loop / 多工具串联 / 多 prompt 架构 / 4 次以上迭代被记录。单步 prompt = 低分。
- **工具选型**:Cowork / Chrome / bash / Skill / MCP / 调度,真正用了哪几样。
- **HIC 智力输入**(权重最高,25 分):分层自评 + N 次迭代被明确记录 + 思路转换被记录 + 失败迭代表格。"50% AI + hand-wave" = 低分。
- **元认知**:做对 / 做错 / Meta-observation 对照 + 修正过的 hand-wave + 深度复盘章节。反思过薄(PDF<2KB) = 低分。
- **可沉淀**:Skill + 配置文件 + launchd / webhook / 跨人复用。方法论 N 条但未做 Skill = 中分。

逐维度过一遍证据,有就标具体事实("CAT Pro + Grafana 监控" / "4 个迭代循环" / "Skill + launchd 周一 9 点跑"),没有就写"无";**绝不**为了凑维度去编。

盘点完毕后,主对话里输出两块,基于步 4 证据 + 步 5.0 回答 + 上述盘点:

- **方向**(2-4 句):从哪儿切入、讲哪几件事、结尾落到哪儿、读者带走什么
- **重点 / 略过**(各 2-4 条):
  - **重点写**:X、Y、Z
  - **略过**:A、B(以及为什么略 —— 一行,如"细节不影响领导判断价值")

这段不是最终文章,是"方向草案 + 取舍清单"给用户拍板用。重点 / 略过显式列出来,用户才能一眼看出哪些被砍,从而否决或换重点。

**5.2 — 一次 `AskUserQuestion`**(`multiSelect: false`),题目模板:

> **<topic 标题>** — 我准备这么写:
>
> [5.1 那段方向 + 重点/略过清单贴在这里]
>
> 按这个写,还是你自己给一个?

options 两个:

1. **label**: "采纳 (推荐)" — **description**: "就按上面这段方向 + 取舍写"
2. **label**: "我自己来" — **description**: "在 Other 里填:重点要 X / 砍掉 Y / 换个切入点 / 你自己的简述 / 任何方向 —— 都行"

处理规则:

- 选 1 → 进步 6,Claude 自己的方向 + 取舍作为主线
- 选 2 + Other 有内容 → Other 内容作为主线,优先级高于四条方向 + Claude 自己的取舍
- 选 2 + Other 为空 → 当作选 1 处理

**关键 UX 教训**(0.1.37 → 0.1.38 改的就是这个):选项 label 不能是"输入类型分类"(大纲 / 简述 / 要点)。那样用户合理地以为选某个类别就会得到那类东西,而不是知道"自己要去 Other 里填"。所以选项必须是**决策**(采纳 / 我自己来),不是**输入形态**。

不要质疑用户给的方向。哪怕你觉得他漏了某个角度,先按他说的写完第一版,后续他自己会发现并补。

## 步 6 — 写第一版

如果步 5 用户给了方向(大纲 / 简述 / 要点),按用户的方向写,**用户的方向是主线**。下面四条方向在用户没给的地方填空、做兜底。

如果步 5 用户选了"你自己看着办",只按下面四条方向写。

这是第一版,**必须**走完步 7(段落重排 + 加小标题) + 步 8(句式打散)才是最终稿。直接落盘第一版 = 周报留着 LLM 默认形状 + 默认节奏 = 一眼被审稿 AI 识破。

四条方向性约束(只指方向,不列规则;v1-v3 历代失败教训:列负面规则等于均值化锚点,见 draft.js 头注):

1. **风格 — 锚 jsonl user 原话**,不锚抽象作者标签(原"王小波口吻"被证伪 —— 模型把它解码成"短句 + 对仗 + 警句"的鸡汤体,反而越打散越像 AI)。具体特征(都是 jsonl 实证,**起草时就奔着这个写,不要先写 LLM 体再返工**):
   - 句长 35-60 字为主,偶尔嵌套长句带技术细节;不要整段都是 20 字左右短句(那是切碎不是参差)
   - 中文逗号 / 句号 + 西文括号补充,**几乎不用 ——**
   - 衔接副词"就 / 但 / 所以 / 再 / 另外 / 反过来"替代 em-dash
   - 第二人称"你"做追问,允许反诘问句("为啥..." / "...吗?")
   - 断言后立刻跟依据(receipts-laden)
   - 不押警句,不押韵收尾,不工整对仗
   - 装饰性 3+ 项 comma 列表每段最多 1 个,且必须是功能性枚举不是对仗
   - 不写"首先 / 其次 / 总之"和工整排比;粗体小标题显式破对仗(不同长度、不同句式、不同人称)
2. **金字塔原理结构**。第一段把结论 + 收益讲完(读者读到这里就该知道做了什么、值不值)。后面才铺关键判断、撞过的墙、细节。线性时间叙事(起因→决定→实现→踩坑→效果)默认不取。
3. **避免"知识的诅咒"**。任何术语、缩写、自造概念,在它第一次出现的位置之前必须已经能站得住 —— 要么是通识,要么前文铺过。需要某个后定义的术语,把解释往前挪,或把那段叙述往后挪。
4. **读者画像:公司领导(技术背景,但不读代码)+ 审稿 AI(按 5.1 那 6 维度查具体事实)**。讲做了什么 + 大致原理 + 价值。领导要"这事值不值",审稿 AI 按 BID / TD / HIC / 元认知 / 可沉淀 / 工具选型 查证据。

   两类读者交集 —— **具体事实 > 通用形容词**。做过的就具体写:
   - 写"4 版迭代,第 2 版改了 prompt 的 X",不写"经过多轮优化"
   - 写"已 launchd 注册周一 9 点跑",不写"已生产部署"
   - 写"文档 99% 是 AI / 迭代逻辑 100% 是我",不写"AI 帮我写完了"

   **加分项**(出现就写):跨周延续(连续两周相关主题被推进)
   **硬扣分项**(出现就 flag,绝不掩盖):重复 hand-wave(上周问题没改)、反思过薄(PDF<2KB)、标题虚标、通用方法论(没和具体业务挂钩)

   **硬性禁止清单**(以下内容除非本身就是结论,否则一律不写):
   - commit hash / PR 号 / issue 号
   - 版本号(0.1.40 这种)、tag、branch 名
   - 具体文件路径(`scripts/lib/draft.js`)、行号、函数名
   - 库名 + 版本号、SDK 调用细节、参数表
   - 例外:数值本身就是结论 —— "砍了 3000 行代码"、"日均 $0.05 → $0.005"、"P99 从 800ms 降到 200ms" —— 可以写
   - 判断标准:把这条删了,领导对"做了什么 + 值不值"的判断会变吗?不变就删
   - 注:加了"审稿 AI"不等于回头塞 commit hash 给 AI 看 —— 审稿 AI 在意的是事实细节的具体性(几版 / 第几版改了什么 / 哪种调度),不是 artifact 真伪

## 步 7 — 段落级重排 + 加小标题(必经)

步 6 写完是按用户方向 / 四条方向铺的第一版,段落骨架很可能仍带 LLM 默认形状(背景 → 起因 → 实现 → 踩坑 → 收尾,或每段一条论点工整排列)。先在段落层动刀,后面步 8 才轮到子句。

做四件事:

1. **结论段强制最前**。第一段必须把"做了什么 + 收益"讲完。如果第一版第一段在铺背景,把结论段从中间拽到最前。
2. **砍冗余段**。任何一段如果删掉之后,领导对"值不值"的判断不变,删。常见嫌疑:背景铺垫段、踩坑回顾段(除非踩坑本身就是价值)、"未来计划"段。
3. **检查硬性禁止清单**(步 6 第 4 条):commit hash / 版本号 / 文件路径 / 行号 / 函数名,逐条搜一遍,不是结论的全删。
4. **每段配 H3 小标题**。一坨连续 paragraph 没人读得下去 —— 每个保留段都得有个能让人扫一眼就懂的 `### ` 小标题,例如"做了什么"、"为什么这么做"、"关键判断"、"踩过的坑"、"收益"、"下一步"。具体用什么标题看内容定,不强制套模板;但**每段都必须有**。标题不工整对仗 —— 长短不一、句式不一,跟步 6 第 1 条的风格规范一致。
5. **补漏已做但没说的事实**。回头看步 5.1 的 6 维度盘点 —— 清单里**有但作文没写**的事实,逐条问"删了这条,领导对'做了什么 + 值不值'的判断会变吗?";变 → 补一句,不变 → 不补。**绝不**为了凑维度去写没做过的事。

重排完段落骨架应该是**头重脚轻**(结论压顶,后面铺关键判断 + 1-2 个细节),不是均匀铺陈;且每段都有 H3 标题把读者眼睛勾住。

## 步 8 — 风格 sanity check(必经,严禁跳过)

> ⚠️ 步 6 第 1 条已经显式要求 jsonl 风格,但 LLM 默认体很有 gravity,起草着起草着就漂回去。这步是最后一道闸,扫一遍把漂回去的拽回来。**跳过 = 整篇前功尽弃**,无论用户催不催、上下文紧不紧、是否觉得"已经够好了",必须过这一遍才能进步 9 落盘。

逐段过一遍,挑出步 6 第 1 条风格规范里的红线项:

- em-dash 自纠 ——X
- 押警句 / 押韵结尾("一样不落"、"源头一换产物跟着换"、"稳了再推" 这类)
- 工整对仗("贵的 X,热的 Y" / "锚 X 挪到 Y")
- 装饰性 3+ 项 comma 列表超过 1 个/段(功能性枚举不算)
- 假 terse 短句堆叠("仿不像。也别扭。")
- 句子工整划一,缺嵌套长句穿插(整段都是 20 字左右短句 = 切碎,不是参差)

发现就**单句重写,不动不破**。改完风格仍以步 6 第 1 条的 jsonl user 原话为准。

**唯一硬约束:通顺**(意思不搞坏 + 读起来不卡)。

注:不是从头逐子句打散每个句子(那是 v3.x SOP 锚点失败模式,见 draft.js 头注 —— 列了"换起头 / 动词 / 修辞 / 句式"清单,清单本身就是新锚点)。这次只针对前述红线项做单点修复,起草时风格已经在步 6 钉死。

## 步 9 — 落盘

```bash
node -e '
const fs = require("fs");
const path = require("path");
const { titleToSlug } = require(process.env.CLAUDE_PLUGIN_ROOT + "/scripts/lib/draft");
const { WEEKLY_DIR } = require(process.env.CLAUDE_PLUGIN_ROOT + "/scripts/lib/paths");
const slug = process.env.WEEK_PREFIX + "-" + titleToSlug(process.env.TITLE);
const folder = path.join(WEEKLY_DIR, slug);
fs.mkdirSync(folder, { recursive: true });
console.log(path.join(folder, slug + ".md"));
' # TITLE=<案例名 或 期号> WEEK_PREFIX=<2026-W20 或 recent-3d>
```

`WEEK_PREFIX` 没 ISO 周时退回 `recent-Nd`。`Write` 落盘到 `~/.ai-best-practice/weekly/<期号>-<slug>/<期号>-<slug>.md` —— 一篇周报一个独立文件夹,后续配图 / excalidraw 源文件 / PDF 之类的兄弟产物都塞进同一个文件夹。

多 topic:一篇 markdown,H1 是期号,每 topic 一个 H2,**每 topic 内部用 H3 分小节**(步 7 第 4 条)。所有 topic 都过完步 5 + 步 6 + 步 7 + 步 8 之后再一次性落盘。落盘前自检:每个 H2 下面至少有 2 个 H3,没有 = 步 7 没做完,回去补。

## 步 10 — 报告

- 输出文件路径
- 未选 topic 列表,每条标涵盖几 session
